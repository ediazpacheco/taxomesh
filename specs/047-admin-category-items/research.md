# Research: 047-admin-category-items

## Decision 1: Which join model to use for the inline?

**Decision**: Use the existing `ItemParentLinkModel` (table `taxomesh_item_parent_link`).

**Rationale**: `ItemParentLinkModel` has two FKs: `item → ItemModel` and `category → CategoryModel`. When Django's `TabularInline` is given this model with `fk_name = "category"`, it automatically filters rows by the current `CategoryModel` instance. No new model or migration is needed.

**Alternatives considered**: A separate through-table was considered but rejected — `ItemParentLinkModel` already represents the item–category placement and is used by `ItemParentLinkInline` on the `ItemModelAdmin`.

---

## Decision 2: Which service methods to call?

**Decision**: Reuse `svc.place_item_in_category(item_id, category_id, sort_index)` for save and `svc.remove_item_from_category(item_id, category_id)` for delete.

**Rationale**: These are the exact same methods used by `ItemParentLinkInline` on the `ItemModelAdmin`. No new service methods are needed. The only difference is that the inline is placed on the `CategoryModelAdmin` rather than `ItemModelAdmin`.

**Alternatives considered**: None — these are the only service methods for this join.

---

## Decision 3: Inline class pattern to follow

**Decision**: Mirror `CategoryChildLinkInline` exactly in structure, substituting `ItemParentLinkModel` and the `item` FK.

**Rationale**: `CategoryChildLinkInline` (044-child-categories-edit) established the pattern for an inline on the `CategoryModelAdmin` that uses the *other* FK direction of a join model. The new inline follows the same pattern: `model = ItemParentLinkModel`, `fk_name = "category"`, `autocomplete_fields = ["item"]`. No custom form is needed because there is no DAG cycle-check for item assignments.

**Alternatives considered**:
- A read-only inline was considered but rejected — the spec requires add and remove.
- A custom change-list link was considered but rejected — the spec explicitly asks for the inline to be on the change page.

---

## Decision 4: No new form class required

**Decision**: Use the default `ModelForm` generated by Django for `ItemParentLinkModel`.

**Rationale**: The only validation needed is the duplicate-link prevention, which is already enforced at the ORM level (`unique_together = [("item", "category")]`) and at the service layer. No additional form-level validation is required.

**Alternatives considered**: A custom form with explicit duplicate-check was considered, but the ORM constraint produces an adequate error message.
